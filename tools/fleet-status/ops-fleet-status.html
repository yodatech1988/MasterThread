Ops Fleet Status

Live, not a point-in-time report — each session writes its own row directly, no relay through the PM. Sibling to the Ops Decision Queue: that page is where you answer things, this one is what's actually running.

liveness, honestly, per panel (2026-09-16)

Genuinely live (subscribed via onSnapshot, updates the instant any session writes, no polling): sessions/teams, the risk banner, the wind-down banner, goals/tasks, blocked, health, costs, the merge queue and open-PRs panels. All of them will reflect a write within about a second of it happening — the mechanism is real.

What "live" does and doesn't mean here: the transport is live for every panel above, but several of them have no session continuously writing to them — they update instantly when someone writes, but nothing writes on a timer. Usage and Cost Inventory say this explicitly in their own panels now (point-in-time facts, not live meters) rather than implying a freshness they don't have.

Confirmed stale right now: the merge-queue and open-PRs panels were seeded from one static sweep and haven't been confirmed as under active write since — they carry their own age-based warning banner rather than looking current by default.

What breaks as the fleet consolidates to 8 seats: nothing about the sessions panel itself — any active session can still write its own doc regardless of headcount. What's genuinely at risk: panels whose only writer is a single named session (the merge queue depends entirely on github-8e; if that seat doesn't survive consolidation, that panel freezes with no replacement writer, silently, unless someone either keeps writing it or the page is told to flag it). This page does not currently detect "my last writer stopped existing" on its own — that would need each panel's writer to be tracked explicitly, which isn't built. Treat any single-writer panel as at risk during the transition and verify by hand rather than trusting the "live" label alone until that's addressed.

Change signal: a panel whose underlying data actually changed pulses once (a brief colored glow around its border, ~2.5s) so a change landing while you're looking at the other monitor is still noticeable when you look back — not just correct in the DOM. No pulse fires on first load, only on a real change after that.

Display mode: append ?wallboard=1 to this page's URL (or use the display-mode link in the top nav) for a large-type, distance-readable layout — same live data, re-laid-out, nothing hidden except this reference footer and the launcher/context copy. A companion launcher script opens it that way on a second monitor without any terminal step.

sessions

Each session keeps its status current by writing its own document directly: db.doc('sessions/<session-name>').set({ session, team, lane, state, committed, uncommitted, waitingOn, nextStep, updatedAt }) — state is one of done / in-flight / blocked / parked, team one of Team A / Team B / Independent. Leave uncommitted empty when there's nothing at risk. A row past ~30 minutes old dims and flags itself stale automatically — that's read from updatedAt, not self-reported, so it can't go silently wrong the way an unreported instruction did tonight. When a session is stood down as part of the fleet's consolidation, set woundDown: true and woundDownAt on its own doc rather than deleting it — the wind-down banner above reads real per-session state, not an assumption about which team goes away.

queue (github-8e writes this)

db.doc('queue/<repo>-<pr>').set({ repo, pr, tier, qcVerdict, qcSummary, authorSession, mergeMethod, dependsOn: [], excluded: false, excludedReason, liveWarning, updatedAt }) — omit dependsOn/liveWarning when not applicable; set excluded: true with a reason for anything held out of the queue entirely.

blocked (anyone can write; cross-link, don't duplicate)

db.doc('blocked/<slug>').set({ title, source, waitingSince, description, decisionQueueUrl, updatedAt }) — if the item already has a card on the Decision Queue, link it via decisionQueueUrl instead of restating it here.

health (any session can update its own topic)

db.doc('health/<topic>').set({ topic, status, detail, updatedAt }) — status is one of ok / warn / crit. Read this before trusting a PR's green or red checks tonight — several are currently meaningless due to known runner-infra gaps, noted here rather than rediscovered per-PR.

prs (any session can refresh its repo's entries)

db.doc('prs/<repo>-<pr>').set({ repo, pr, title, qcState, url, updatedAt }) — qcState is one of pending / pass / fail / n/a.

goals + tasks (the 93-task work tree, individually tracked)

goals/<phase> holds phase metadata only: { phase, name, exit, updatedAt }. Each of the 93 tasks is its OWN document — db.doc('tasks/<id>').set({ id, phase, title, owner, size, hold, deps: [], note, status, updatedAt }) — so any session can update one task's status without touching the other 92. owner is you / agent / both; status is done or unknown — never invent in-progress/blocked/etc. unless the source plan itself records it; absence of evidence stays unknown, visibly, not a guessed "not started."

costs (any session can update its own system's row)

db.doc('costs/<slug>').set({ system, bucket, monthlyCost, measured, source, notes, updatedAt }) — bucket is one of subscription / measured / unreachable / not-built; monthlyCost is a number in dollars or null if genuinely unknown — never a guess presented as real; measured: false with a number means an estimate, labeled as one. Real API figures only — never derive a dollar amount from transcript token counts (the 4.7× over-report problem applies to money the same as it does to the usage panel).
